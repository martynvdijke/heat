## Context

The app currently supports multiple seasons, each with a status (active/archived). Round snapshots track per-round standings and can be finalized to apply points to racers. However:

- `round_snapshots.season_id` is optional (`.Optional().Default(1)` in ent schema) with no foreign key — rounds can exist without a valid season or be moved between seasons.
- The "Take Snapshot" admin UI defaults to season_id=1 when none is provided, rather than using the active season.
- When a round is finalized (`FinalizeRound` handler), driver points and stats are updated but no email notifications are sent, even though the email infrastructure exists (`SendRaceEmail`, `SendRaceEmailManual`).
- The email system currently works with `race_history` table data (race results from actual races), not with round snapshot data.

## Goals / Non-Goals

**Goals:**
- Enforce at the database level that each round belongs to exactly one season and round numbers are unique per season
- Ensure all round creation paths validate and require a season_id
- Send email notifications to racers when a round is finalized, using the round snapshot scores as content
- Keep the admin UI consistent: snapshot creation always targets the active season

**Non-Goals:**
- Changing the existing race-based email sending flow
- Adding push/Gotify notifications on round finalize (only email)
- Reworking the season archiving logic beyond the foreign key validation already in place

## Decisions

1. **Database constraints over application-only validation**: We'll use both a NOT NULL + FK constraint and a UNIQUE(season_id, round) constraint rather than only checking in Go code. This ensures data integrity even if new code paths or direct DB writes bypass validation.

2. **Migration strategy**: Since the schema was originally generated by ent (code-first), we'll write raw SQL migrations rather than modifying the ent schema and regenerating. The ent schema will be updated to reflect the new constraints, but we'll apply the actual DB changes via ALTER TABLE statements with a migration step for existing data.

3. **Reuse `SendRaceEmail` with round data**: Rather than creating a separate email function for round finalization, we'll adapt the existing `SendRaceEmail` to also work with round snapshot data. The `FinalizeRound` handler will call a new `SendRoundEmail` function that fetches round scores and sends them out — structurally identical to `SendRaceEmail` but sourcing data from `round_snapshot_scores` instead of `race_results`.

4. **Async email sending**: Emails will be sent asynchronously (goroutines) to avoid blocking the finalize response, matching the existing pattern in `SendRaceEmail`.

## Risks / Trade-offs

- **Data migration needed**: Existing `round_snapshots` rows may have `season_id = NULL` or `season_id = 0`. These will need to be backfilled to a valid season (likely season 1 or the active season).
- **Foreign key with SQLite**: SQLite supports foreign keys but they must be enabled via `PRAGMA foreign_keys = ON`. The app must ensure this pragma is set at connection time.
- **Unique constraint violation**: If existing data has duplicate (season_id, round) combinations, the migration will fail. A deduplication step is needed first.
